[검토 요청] 스마트캠핑플랜 행동-태그 시스템 개선 제안
0. 전제

현재 구조는 맞다.

스마트캠핑플랜은 이미 ContextFit = weather_match + persona_match 구조를 가지고 있고, 4축 점수(Existence/Quality/ContextFit/Logistics)로 최종 선별하는 엔진이다.

행동-태그 정의서는 Event-Triggered Tagging, Controlled Vocabulary, Time-Decay를 원칙으로 하고, 50개 태그 + 50개 액션 규칙으로 페르소나를 누적시키는 구조다.

현재 일부 예약 액션만 적용되어 있고, 커뮤니티/LBS/스마트플랜 상호작용은 대부분 미적용 상태다.

문제는 방향이 아니라, 구현 단위가 아직 느슨하다는 점이다.

1. 핵심 문제 4개
1-1. user_personas.tags 단일 누적 구조만으로는 부족

지금 방식만으로는 아래가 어렵다.

왜 이 태그가 올라갔는지 추적

시간 감쇠 재계산

추천 근거 설명

잘못된 누적 롤백

1-2. 태그 문자열 정규화가 불안정

정의서 안에서도 #노지/차박과 #차박/노지가 섞여 있다.
이 상태면 DB에서 다른 태그로 쌓일 수 있다.

1-3. persona_match 브리지 레이어가 부족

스마트플랜은 이미 persona_match를 점수에 반영한다.
하지만 현재는 “어떤 사용자 태그가 어떤 장소 속성과 만나면 몇 점을 주는지”가 예시 수준이지, 엔진이 그대로 계산할 수 있는 표준 규칙 테이블 수준은 아니다.

1-4. Strong / Medium / Weak 신호가 섞여 있음

문서 원칙은 Strong Signal 중심인데, 실제 액션에는 체류/탭 클릭 같은 약한 신호도 포함되어 있다.
이걸 같은 방식으로 누적하면 추천이 흔들릴 수 있다.

// 1) 원본 행동 로그
type UserActionLog = {
  id: string;
  userId: string;
  tripId?: string | null;
  sessionId?: string | null;
  actionType: string;        // RESERVATION_COMPLETED, PLAN_SWAP_RESTAURANT ...
  objectType?: string | null; // PLAN_CARD, PLACE, POST ...
  objectId?: string | null;
  meta?: Record<string, any>;
  occurredAt: string;
  dedupeKey?: string | null;
};

// 2) 행동 -> 태그 반영 ledger
type UserTagLedger = {
  id: string;
  userId: string;
  actionLogId: string;
  canonicalTagId: string;
  deltaScore: number;
  signalStrength: "STRONG" | "MEDIUM" | "WEAK";
  confidence: number; // 0~1
  occurredAt: string;
};

// 3) 장기 성향 snapshot
type UserPersonaSnapshot = {
  userId: string;
  tagScores: Record<string, number>;
  topTags: string[];
  updatedAt: string;
};

// 4) 이번 일정 전용 snapshot
type TripPersonaSnapshot = {
  tripId: string;
  userId: string;
  tripTagScores: Record<string, number>;
  constraints: Record<string, any>; // withKids, withPet, winterMode ...
  updatedAt: string;
  expiresAt: string;
};

user_persona_snapshot: 빠른 조회

trip_persona_snapshot: 이번 여행 의도 분리

4. 최소 구현 플로우 제안
// 1. 사용자가 행동
logUserAction(action)

// 2. 행동 -> 태그 ledger 생성
applyActionToTags(action)

// 3. snapshot 갱신
rebuildPersonaSnapshot(userId)
rebuildTripPersonaSnapshot(userId, tripId)

// 4. 스마트플랜 실행 시 persona_match 계산
const personaMatch = computePersonaMatch({
  fact,
  globalPersona,
  tripPersona,
  weatherContext,
})

// 5. 기존 ContextFit에 합산
ContextFit = weather_match + persona_match

스마트플랜은 이미 ContextFit과 finalScore 구조가 있으니,
태그 시스템은 새 추천 엔진을 만드는 게 아니라 persona_match 공급층만 정확히 붙이면 된다.

6. 한 줄 결론

행동-태그 시스템은 유지하되, “문자열 태그 누적”에서 “정규화된 태그 ledger + persona bridge 기반 persona_match 계산” 구조로 올리는 것이 핵심입니다.
